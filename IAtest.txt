Résultats obtenus

L’analyse du repository SABR Simulateur met en évidence plusieurs limites concernant la fiabilité et l’exhaustivité de la documentation générée :

* Hallucinations fonctionnelles : RetroDoc attribue au simulateur des responsabilités qu’il ne porte pas, notamment la gestion des comptes. Cette fonctionnalité ne relève pas du périmètre réel du composant.
* Inventaire incomplet des messages : la liste des messages échangés n’est pas exhaustive. Certains messages sont présentés comme les « messages principaux », sans justification de ce caractère représentatif.
* Confusion sur les responsabilités applicatives : RetroDoc attribue au simulateur des traitements réellement exécutés par le moteur SABR, alors que le simulateur se limite à déclencher des appels ou à interagir avec ce dernier.
* Surinterprétation des tests : l’outil s’appuie fortement sur les scénarios de tests pour décrire le fonctionnement de l’application, au risque de confondre les comportements effectivement implémentés avec les cas de test.
* Analyse insuffisante des échanges asynchrones : la description des API REST est globalement satisfaisante. En revanche, les échanges par messagerie (Kafka, ActiveMQ, etc.) sont peu ou mal documentés. Leur identification nécessite des instructions explicites dans le prompt personnalisé ; le template par défaut ne permet pas de les restituer correctement.

Améliorations proposées

* Fiabiliser l’analyse fonctionnelle : distinguer explicitement les responsabilités propres au composant de celles des systèmes externes appelés.
* Améliorer la traçabilité : associer chaque fonctionnalité identifiée aux classes, méthodes ou configurations qui justifient son existence.
* Garantir une meilleure exhaustivité des messages : inventorier les messages entrants et sortants en précisant leur type, leur canal, leurs producteurs et leurs consommateurs, lorsque ces informations sont identifiables.
* Distinguer code applicatif et code de test : privilégier le code de production comme source de référence pour la documentation fonctionnelle. Utiliser les tests comme éléments complémentaires de validation.
* Renforcer la prise en charge des architectures événementielles : détecter automatiquement les producteurs, consommateurs, topics Kafka, queues ActiveMQ, formats de messages et flux asynchrones, sans nécessiter de prompt spécifique.
* Améliorer le template par défaut : intégrer une section dédiée aux échanges interapplicatifs, synchrones et asynchrones, ainsi qu’une cartographie des flux.
* Limiter les hallucinations : signaler explicitement les éléments non vérifiables plutôt que de présenter des déductions comme des fonctionnalités avérées.
