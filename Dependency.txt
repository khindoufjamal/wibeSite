Guide technique complet — RTL-1463

Projet RTL · Java / Maven · GitLab CI · Trivy · Migration Quarkus à venir

L’objectif est que tu puisses avancer sur les tickets Jira de manière autonome, depuis l’analyse du projet jusqu’à la création des Merge Requests, en sachant précisément quelles commandes exécuter, quels fichiers modifier et comment vérifier tes corrections.

Je pars de ton rapport Trivy et surtout des dernières consignes de Shien-Haur.

1. La stratégie validée avec Shien-Haur

Son instruction change la manière d’aborder le chantier :

Procéder par ce qui est le plus simple en premier : toutes les versions patch, puis les versions mineures, puis ZooKeeper et Hazelcast aussi loin que possible sans toucher au middleware. Les CVE restantes pourront être traitées dans le cadre de la migration Quarkus.

Cela signifie qu’on ne cherche pas à faire disparaître les 76 vulnérabilités à n’importe quel prix.

Ordre opérationnel

* RTL-1452 — Correctifs patch
    Passer de X.Y.Z à X.Y.Z+n quand cela corrige des CVE sans changer de génération.
* RTL-1455 — Correctifs mineurs
    Passer de X.Y à X.Y+n, après contrôle de compatibilité.
* RTL-1453 — ZooKeeper
    Évaluer la version compatible avec le cluster et le middleware existants.
* RTL-1454 — Hazelcast
    Vérifier jusqu’où monter sans migration de cluster ni changement majeur non maîtrisé.

Règles de décision

Situation	Décision
Patch compatible et tests OK	Corriger
Mineure compatible et tests OK	Corriger
Mise à jour provoquant des erreurs de compilation	Analyser puis ajuster dans le périmètre prévu
Migration majeure nécessitant Java/Jakarta/Quarkus	Différer et documenter
Modification du middleware obligatoire	Ne pas engager sans validation de Shien-Haur
CVE sans correctif compatible	Documenter le risque et le report

Attention : la consigne autorise un report technique, pas l’acceptation automatique du risque de sécurité. Les vulnérabilités critiques restantes devront être remontées et faire l’objet de la validation sécurité habituelle.

Phase 1 — Préparation de l’environnement

Étape 1 : se placer dans le projet

Dans le terminal IntelliJ ou un terminal macOS :

# Se placer à la racine du dépôt
cd /chemin/vers/rtl
# Vérifier le dépôt
pwd
git status
git branch --show-current
# Vérifier les outils
java -version
mvn -version
git --version
# Vérifier si Maven Wrapper est disponible
ls -la mvnw .mvn 2>/dev/null

Si le projet fournit ./mvnw, utilise-le de préférence à mvn pour reprendre la version Maven prévue par l’équipe.

Vérifie également la version Java réellement utilisée dans GitLab CI. Une compilation locale avec Java 21 peut fonctionner alors que le pipeline utilise Java 17, ou inversement.

Étape 2 : créer la branche de travail

Commence avec RTL-1452, en te basant sur la branche de référence de ton équipe (par exemple develop, à confirmer).

git fetch origin
# Exemple si la branche de référence est develop
git switch develop
git pull --ff-only origin develop
# Créer une branche dédiée
git switch -c fix/RTL-1452-dependencies-patch

Ne mélange pas les modifications des quatre sous-tâches dans un même commit.

Étape 3 : vérifier que le projet compile avant modification

Depuis la racine du reactor Maven :

mvn -pl rtl-core/rtl-application-web -am \
  clean verify 2>&1 | tee /tmp/rtl-baseline-build.log

Avec cette commande :

* -pl sélectionne le module.
* -am construit également les modules du reactor nécessaires.
* clean supprime les anciens résultats de compilation.
* verify exécute les phases prévues par le cycle Maven, dont les tests configurés.
* tee conserve le log pour analyse.

Sur macOS, si tu veux que la commande retourne bien l’échec Maven même lorsqu’elle est suivie de tee, exécute set -o pipefail avant la commande.

Résultat attendu : BUILD SUCCESS.

Si le build échoue avant toute modification, il faut isoler la cause : configuration Maven, dépôts internes, tests, profils, variables d’environnement ou état initial du code.

Phase 2 — Analyse des dépendances Maven

C’est la phase la plus importante. Avant de modifier une version, tu dois comprendre d’où elle vient.

Étape 4 : générer le dependency tree

Depuis la racine :

mkdir -p /tmp/rtl-audit
mvn -pl rtl-core/rtl-application-web \
  dependency:tree \
  -DoutputType=text \
  -DoutputFile=/tmp/rtl-audit/dependencies-before.txt

Ce fichier permettra de voir les dépendances directes et transitives réellement résolues par Maven. Apache Maven Dependency Plugin

Exemple fictif :

rtl-application-web
 +- com.example:legacy-client:jar:1.0
 |  \- com.fasterxml.jackson.core:jackson-databind:jar:2.18.3
 +- org.postgresql:postgresql:jar:42.7.10

Dans cet exemple :

* PostgreSQL est déclaré directement.
* Jackson vient d’une autre librairie.
* Netty peut être direct ou transitif selon la déclaration réelle.

Le traitement sera différent pour chaque cas.

Étape 6 : retrouver l’origine des versions

Génère le POM effectif, incluant l’héritage du parent, les profils actifs et les versions gérées :

mvn -pl rtl-core/rtl-application-web \
  help:effective-pom \
  -Dverbose \
  -Doutput=/tmp/rtl-audit/effective-pom.xml

Le mode verbose permet de repérer l’origine des éléments dans le POM lorsque le plugin le prend en charge. Apache Maven Help Plugin

Puis recherche les librairies :

grep -n -E \
  'jackson|postgresql|hazelcast|zookeeper|netty|spring|quarkus' \
  /tmp/rtl-audit/effective-pom.xml

Pour chaque dépendance, note le mode de gestion :

Origine de la version	Action
Propriété <xxx.version>	Modifier la propriété concernée
 parent	Modifier l’entrée centralisée
BOM importé	Vérifier s’il faut monter le BOM
Version dans la dépendance locale	Modifier dans le POM du module
Dépendance transitive	Mettre à jour le parent responsable, sinon gérer explicitement après analyse

Règle Maven : ne commence pas par ajouter des versions partout dans les POM. Cela peut neutraliser la gestion centralisée et introduire des incompatibilités.

Phase 3 — RTL-1452 : monter toutes les versions patch

C’est ton premier ticket à développer.

Étape 7 : identifier les patchs disponibles

Un patch correspond, dans la convention habituelle MAJOR.MINOR.PATCH, à une modification du dernier numéro.

Exemples :

* 42.7.10 → 42.7.12 : patch.
* 2.18.3 → 2.18.11 : patch.
* 1.1.10.7 → 1.1.10.9 : révision dans la même branche.
* 3.5.7 → 3.6.12 : changement mineur.
* 4.2.8 → 5.7.0 : changement majeur.

Attention : toutes les librairies ne suivent pas parfaitement SemVer.

Commande pour afficher les patchs Maven

mvn -pl rtl-core/rtl-application-web \
  versions:display-dependency-updates \
  -DallowMajorUpdates=false \
  -DallowMinorUpdates=false

Cette commande affiche les mises à jour compatibles avec les contraintes de segments de version du plugin. Elle ne modifie pas les POM. Versions Maven Plugin

Si les versions sont gérées par des propriétés :

mvn -pl rtl-core/rtl-application-web \
  versions:display-property-updates \
  -DallowMajorUpdates=false \
  -DallowMinorUpdates=false

Garde les résultats du diagnostic dans un fichier de travail.

Étape 8 : choisir les versions à appliquer

Pour chaque librairie :

* Identifier la version Maven réellement résolue.
* Chercher les patchs disponibles dans la même branche.
* Vérifier le correctif dans les release notes et le rapport de sécurité.
* Choisir la version compatible qui corrige le plus de CVE.
* Vérifier que le dépôt Maven interne de l’entreprise dispose de cette version.

Pour confirmer qu’un artefact existe dans les dépôts Maven configurés :

mvn dependency:get \
  -Dartifact=org.postgresql:postgresql:42.7.12 \
  -Dtransitive=false

Si le téléchargement échoue, cela peut provenir d’une version indisponible, de Nexus/Artifactory, de droits insuffisants ou d’une configuration Maven défaillante.

Exemple pratique : PostgreSQL

Si le POM contient :

<properties>
    <postgresql.version>42.7.10</postgresql.version>
</properties>

Tu modifies uniquement :

<properties>
    <postgresql.version>42.7.12</postgresql.version>
</properties>

Si la version est directement dans la déclaration <dependency>, modifie cette déclaration au lieu de créer une propriété inutile.

Ensuite :

# Vérifier la version résolue
mvn -pl rtl-core/rtl-application-web \
  dependency:tree \
  -Dincludes=org.postgresql:postgresql
# Reconstruire l'application
mvn -pl rtl-core/rtl-application-web -am \
  clean verify

Tu dois constater que la version résolue est bien celle attendue. Le changement du texte du POM ne suffit pas.

Étape 9 : traiter les dépendances transitives

Prenons un exemple fictif :

rtl-application-web
  └── client-service:2.0
       └── io.netty:netty-handler:4.1.63.Final

Si Netty arrive par client-service, tu as trois possibilités.

Option 1 — Mettre à jour la bibliothèque parente. C’est généralement le meilleur choix lorsque la nouvelle version de client-service gère un Netty corrigé.

Option 2 — Mettre à jour le BOM. Si tous les modules Netty sont gérés par un BOM, privilégie l’alignement global.

Option 3 — Forcer une version corrigée. À réserver aux cas où la compatibilité est établie.

Exemple de dependencyManagement pour imposer la version d’un artefact :

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>io.netty</groupId>
            <artifactId>netty-handler</artifactId>
            <version>${netty.version}</version>
        </dependency>
    </dependencies>
</dependencyManagement>

Cela ne suffit pas à aligner automatiquement tous les composants Netty : il faut vérifier l’ensemble du graphe et, si nécessaire, utiliser le BOM Netty correspondant.

N’ajoute pas d’exclusion transitive sans avoir identifié précisément pourquoi elle est nécessaire. Une exclusion incorrecte peut supprimer une bibliothèque utilisée à l’exécution.

Il ne faut pas considérer automatiquement toutes ces mises à jour comme mineures : certaines nécessitent de franchir plusieurs générations ou de changer de framework.

Exemple : Kafka Clients

Avant de modifier kafka-clients, identifie :

* La version des brokers Kafka.
* La version de Spring Kafka.
* Le mode d’authentification SASL/SSL.
* Les serializers et deserializers utilisés.
* Les options producteur et consommateur.

Après modification, vérifie les échanges réels :

* Production d’un message.
* Consommation.
* Commit des offsets.
* Gestion des erreurs.
* Reconnexion au broker.
* Compatibilité de la sérialisation.

Une compilation réussie ne prouve pas que la connexion au Kafka de l’environnement fonctionne encore.

Point sensible : Spring

Ne monte pas spring-core indépendamment du reste des composants Spring. Une version de spring-web, spring-expression ou spring-data-commons incompatible peut provoquer des erreurs NoSuchMethodError, ClassNotFoundException ou des échecs au démarrage.

Si la seule correction disponible impose une migration Jakarta ou une nouvelle génération Java, conserve ce changement pour le chantier de migration Quarkus, sous réserve de l’arbitrage sécurité.

* Déterminer si ZooKeeper est direct ou transitif.
* Relever la version du serveur sur l’environnement de recette.

* Choisir une version corrigée supportée.
* Modifier la gestion Maven.
* Compiler et tester les connexions.
* Vérifier les logs au démarrage.
* Valider la reconnexion après interruption.

Si la mise à jour nécessite d’intervenir sur les serveurs, arrête le changement à la frontière convenue avec Shien-Haur et documente les limitations.

Phase 6 — RTL-1454 : Hazelcast

Étape 13 : analyser Hazelcast avant toute montée

C’est probablement la partie la plus sensible au niveau du middleware.

Élément	Valeur
Artifact	com.hazelcast:hazelcast
Version actuelle	4.2.8
CVE critique visible	CVE-2026-107726
Version corrigée affichée	5.7.0

Le passage de Hazelcast 4.2.8 vers 5.7.0 est majeur. Il ne faut donc pas l’appliquer automatiquement, surtout après les consignes de Shien-Haur.

Commandes de diagnostic

mvn -pl rtl-core/rtl-application-web \
  dependency:tree \
  -Dincludes=com.hazelcast:*

Pour identifier les usages :

grep -R -n -E \
  'HazelcastInstance|HazelcastClient|IMap|IQueue|EntryProcessor|hazelcast' \
  --include="*.java" \
  --include="*.xml" \
  --include="*.yaml" \
  --include="*.properties" \
  .

Ce qu’il faut déterminer

* Le projet embarque-t-il un membre Hazelcast ou se connecte-t-il comme client ?
* Le cluster est-il partagé avec d’autres applications ?
* Est-ce que les instances RTL partagent le même cache ?
* La configuration est-elle XML, YAML ou Java ?
* Quelle est la version Hazelcast côté infrastructure ?
* Existe-t-il une version corrigée compatible dans la branche 4.x ?

Si la dernière réponse est non, le ticket peut déboucher sur une analyse de faisabilité et un report justifié, plutôt qu’une modification forcée.

Tests nécessaires si la mise à jour est compatible

* Démarrage de l’application.
* Connexion au cluster.
* Lecture et écriture du cache.
* TTL et expiration.
* Sérialisation des objets Java.
* Fonctionnement avec deux instances RTL.
* Reconnexion après indisponibilité.
* Absence d’erreur dans les logs.

À ne pas faire : changer le numéro de version Hazelcast dans le POM puis pousser directement vers la recette sans vérifier la compatibilité des membres du cluster.

Étape 15 : relancer Trivy

Le plus fiable est d’utiliser le même scanner, la même configuration, le même périmètre et le même type d’artefact que GitLab CI.

Pour un contrôle local préliminaire :

trivy --version
trivy fs \
  --scanners vuln \
  --severity HIGH,CRITICAL \
  --format json \
  --output /tmp/rtl-audit/trivy-after.json \
  rtl-core/rtl-application-web

La syntaxe trivy fs et le filtre de sévérité sont documentés par Trivy. Trivy

Attention : un scan local du répertoire Maven et un scan du WAR/JAR construit peuvent renvoyer des résultats différents. Le pipeline GitLab reste ta référence de validation.

Extraire les vulnérabilités avec jq

Si tu disposes du rapport JSON :

jq -r '
  .Results[]?
  | .Vulnerabilities[]?
  | [
      .PkgName,
      .InstalledVersion,
      .FixedVersion,
      .Severity,
      .VulnerabilityID
    ]
  | @tsv
' /tmp/rtl-audit/trivy-after.json

Tu obtiendras un tableau de ce type :

Package       Installed  Fixed    Severity  CVE
postgresql    42.7.10    42.7.12 HIGH      CVE-...
hazelcast     4.2.8      5.7.0   CRITICAL  CVE-...
zookeeper     3.6.3      3.8.3   CRITICAL  CVE-...

C’est un exemple de structure, pas un nouveau résultat de scan.

Calculer les totaux

jq -r '
  [.Results[]?.Vulnerabilities[]?]
  | group_by(.Severity)
  | .[]
  | "\(.[0].Severity): \(length)"
' /tmp/rtl-audit/trivy-after.json

Ne masque pas les vulnérabilités sans correctif : l’option --ignore-unfixed les retirerait de l’affichage, mais ne les corrigerait pas. Trivy

Étape 16 : comparer les rapports avant / après

Le mieux est de sauvegarder deux rapports JSON produits de manière identique :

* trivy-before.json
* trivy-after.json

Pour lister les identifiants vulnérables initiaux :

jq -r '
  .Results[]?
  | .Vulnerabilities[]?
  | [.PkgName, .VulnerabilityID]
  | @tsv
' /tmp/rtl-audit/trivy-before.json \

Puis les identifiants restants :

  | .Vulnerabilities[]?

  | @tsv
' /tmp/rtl-audit/trivy-after.json \
  | sort -u > /tmp/rtl-audit/cve-after.txt

Afficher les vulnérabilités disparues :

  /tmp/rtl-audit/cve-before.txt \

Afficher les nouvelles vulnérabilités détectées :

Cette comparaison donne une première vue pratique. Pour un audit complet, compare aussi les versions, la sévérité, le chemin du module et les changements de base de données Trivy.

Étape 18 : comprendre les erreurs les plus fréquentes

Erreur	Cause possible	Action
Could not resolve dependencies	Version absente du repository ou accès impossible	Vérifier artefact, Nexus, settings et credentials
NoSuchMethodError	Incompatibilité binaire entre JAR	Inspecter le dependency tree et aligner les versions
ClassNotFoundException	Dépendance absente ou incompatible	Vérifier dépendances transitives et exclusions
UnsupportedClassVersionError	Version Java incompatible	Vérifier Java local, CI et compilation
NoClassDefFoundError	Classe absente au runtime	Vérifier le contenu du WAR/JAR et les scopes
Failed to load ApplicationContext	Incompatibilité Spring ou configuration	Vérifier les versions coordonnées et le premier Caused by
javax.* / jakarta.*	Migration d’API incompatible	Ne pas forcer une migration majeure hors périmètre

Recherche d’une erreur dans les logs

grep -n -E \
  'BUILD FAILURE|Caused by:|NoSuchMethodError|ClassNotFoundException|UnsupportedClassVersionError' \
  /tmp/rtl-baseline-build.log

Ne te contente pas de la dernière ligne de Maven. La cause utile est souvent plus haut, dans le premier Caused by.

Étape 19 : en cas d’échec après une montée

Procédure :

* Identifie la dernière modification Maven.
* Vérifie que la nouvelle version a bien été résolue.
* Consulte la première erreur de compilation ou d’exécution.
* Vérifie les dépendances transitives modifiées.
* Compare les release notes.
* Corrige uniquement ce problème si cela reste dans le périmètre.
* Sinon, annule la mise à jour et documente le blocage.

Pour inspecter l’état des changements :

git diff --check
git diff --stat
git diff

Pour annuler seulement un fichier modifié et non encore commité, lorsque tu es certain de ne pas vouloir conserver son contenu :

git restore -- chemin/vers/pom.xml

Évite git reset --hard, qui pourrait faire perdre d’autres modifications locales.
